# Start page development

The production page is still generated by `npm run build`: RSS is fetched at build time, and `dist/` contains static HTML, CSS, JavaScript, and a small version manifest for GitHub Pages.

## Tests

| Command | Purpose |
| --- | --- |
| `npm test` | Run Vitest unit tests once. |
| `npm run test:watch` | Run Vitest in watch mode. |
| `npm run test:browser` | Run Playwright Chromium tests against a local fixture-built page. |
| `npm run test:all` | Run unit and browser tests. |

After `npm ci`, install the browser once with `npx playwright install chromium`. CI uses `npx playwright install --with-deps chromium` to include Linux browser prerequisites. Safari remote automation is not needed.

Unit tests live in `tests/*.test.mjs`. Browser tests live in `tests/browser/*.spec.mjs`; their data is in `tests/fixtures/`. Playwright starts `tests/browser/serve-fixtures.cjs`, which calls the real build generator with fixed feed data and build time, serves a temporary output directory on `127.0.0.1:4173`, and removes it when the server stops. Browser tests never fetch live RSS or submit requests to external search services.

The visual tests use the open IBM Plex Mono files from a **development dependency**. The test server provides them only to the fixture page; the production page still prefers an installed Berkeley Mono and downloads no font. The test clock is fixed. The 1024 × 576, 853 × 480, 1152 × 720, and 960 × 600 checks exercise reduced **CSS viewport sizes** representative of browser zoom, not the browser's zoom setting itself.

## Screenshot baselines

Baselines are in `tests/browser/__screenshots__/` for 1280 × 720 and 1440 × 900. Run `npm run test:browser` to compare them. On failure, inspect the actual, expected, and diff images in `test-results/`; `npx playwright show-report` opens the HTML report if one was generated. For traces, run `npx playwright show-trace test-results/<test-name>/trace.zip`.

The dense, text-heavy dashboard snapshots are compared on macOS, where they were authored. On Linux, those same tests assert exact shell geometry, theme colors, and test-font selection; the browser suite also checks panel geometry, wrapping, overflow, interactions, accessibility, and the remaining dialog/help snapshots. macOS developers can run the Linux-style assertions with `DASHBOARD_VISUAL_MODE=structure npm run test:browser`. Chromium rasterizes text differently across operating systems even with the same test font, so do not update macOS baselines from a Linux run. After an intentional visual change, review the rendered result on macOS, then run `npm run test:browser -- --update-snapshots` there and inspect the changed images before retaining them. Do not update baselines just to clear a failure.

The GitHub Actions publishing job runs unit tests, installs Chromium, runs browser and accessibility tests, then runs the live production build. Any failed required check prevents deployment.

## RSS workspace layout

The generated feed panels remain the source of content. `src/dashboard.js` places those same elements into two column stacks and paginates them according to the measured RSS content height. Panels require at least 244 CSS pixels, with 8-pixel gaps and outer padding. At a narrow 853px desktop viewport, this height exposes two representative wrapped headlines, including with a 12px classic scrollbar gutter; 226px clipped the second on Ubuntu. At 1280 × 720, four feeds fit per page; at 1440 × 900, six fit. A 960 × 600 viewport fits one row per page. A `ResizeObserver` recalculates capacity, retaining a focused feed or the first feed on the visible page as an anchor. Page selection resets on reload. Feed scroll offsets are restored when panels move, subject to browser scroll clamping if their new height is smaller.

With JavaScript unavailable, the original generated grid remains scrollable and all feeds remain in the document. If the RSS area is shorter than one usable panel, JavaScript shows a window-size message instead of compressing the panels. The browser fixture server also exposes `/many/`, `/one/`, and `/none/` for deterministic feed-count tests. Its viewport tests reduce CSS viewport dimensions to approximate zoom constraints; they do not change browser zoom itself.

RSS dates are normalized to full UTC ISO timestamps during the build. Generated `<time>` elements show an absolute UTC date without JavaScript and retain an exact UTC date and time in their attributes. One browser timer updates the visible labels once per minute to `now`, minutes, hours, days, or weeks. Missing and invalid dates produce no timestamp. Headline lists use native, individually scrollable panels with thin Gruvbox scrollbars.

## Reserved workspace

The right workspace has three intentionally nonfunctional regions: a full-width Metrics slot above separate Home and Utilities slots. Their labels and borders mark space for future dashboard features; each region can be replaced as functionality is added.

## Keyboard use

Search retains autofocus. Outside editable fields, `/` focuses and selects its query, `?` opens native dialog help, and `Escape` in search moves focus to the visible RSS page. Left and right arrows change RSS pages only while focus is in the RSS workspace and another page exists. Tab, Shift+Tab, and Enter retain native browser behavior. The footer help button provides mouse and keyboard access to the same instructions. The dialog closes with Escape or its close button and restores the opener's focus where possible.

## Build status and updates

The build reads the hourly `0 * * * *` schedule from `.github/workflows/build.yml` and creates one metadata record from its full UTC timestamp and actual feed results. In GitHub Actions, the version includes the run ID and attempt; local builds use a UUID. The record is embedded in `index.html`, and `version.json` contains the same version and timestamp. CSS and local script URLs carry the version as a cache key. Changing the workflow schedule away from the supported hourly form requires updating the countdown calculation; the build fails instead of displaying an incorrect schedule.

The footer reports health for the **loaded** page and counts down to the next expected UTC schedule boundary. Once a scheduled boundary passes without newer published content, it says `AWAITING UPDATE`; this does not assert that a workflow ran or failed. Build details show the exact loaded timestamp, version, feed failures, schedule, and confirmed update state. Without JavaScript, the generated footer still shows the exact build timestamp and feed count.

The browser checks `version.json` on load, about every five minutes while visible, and when the tab becomes visible or returns online. It bypasses cache for both the manifest and a verification request for `index.html`; the update control appears only when their versions and timestamps match. This is a same-origin check, not an RSS or GitHub API request. Refresh is always manual, by button or `R` outside editable fields and dialogs. A failed or mismatched check leaves the current page intact and is retried later. GitHub Pages CDN propagation can briefly make the manifest and HTML disagree; the handshake suppresses an update during that interval. A local build cannot prove CDN ordering, so verify this once after deployment.
